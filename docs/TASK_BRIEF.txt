01  业务背景
公司举办若干名额有限的技术活动。用户需要浏览活动、报名并查看自己的报名记录。高峰时会多人争抢最后几个名额；用户也可能因网络超时重复点击。请实现一个能够正确处理这些情况的最小系统。

02  业务规则与边界
报名必须满足的规则
规则
精确定义
名额
每次成功报名占用 1 个名额。剩余名额不能为负；总名额 = 剩余名额 + 成功报名数。
业务去重
同一用户对同一活动只能成功报名一次；换一个 requestId 也不能多占名额。
原子性
报名记录与名额扣减必须一起提交、一起回滚，不能出现扣了名额但没有记录。
请求键
requestId 为 1—64 位 ASCII 字符，匹配 [A-Za-z0-9_-]{1,64}，区分大小写；作用域是当前用户。
成功重放
同一用户、同一键、同一 activityId 重试，返回原报名记录，不再次扣减。
参数冲突
同一用户把已成功绑定的键用于另一活动，返回冲突；不能创建第二条记录。
失败请求
只有成功提交的报名才绑定 requestId。失败请求不占用该键。
并发请求
同键并发收敛到同一报名 ID；同用户换键并发只允许一次成功；不能向客户端直接泄露唯一键异常。
判定顺序
先校验身份标记与参数。已成功请求的重放／参数冲突、已有报名判定，应先于活动当前满额或关闭的判定。已经成功的请求，即使活动随后满额，也应能返回原记录。
跨活动并发复用同一用户的同一键时，只允许一个活动成功绑定；另一个返回参数冲突，并且不能多扣任何活动的名额。对可预见的竞争，应给出约定的业务响应，而不是 500。
演示身份与数据隔离
报名相关 API 使用 X-User-Id 请求头，值为正整数。缺失、非数字或非正数均返回 400。查询报名时服务端必须限制为当前标记用户；查看他人记录与不存在记录统一返回 404。
X-User-Id 只是本机演示标记，不是生产级认证。无需实现登录，但需在设计说明中明确这一限制；不要将本题用户隔离测试宣称为完整安全认证。
项目组织由你决定
不要求特定包名、DDD 层级或接口数量。请在实际代码中体现 HTTP 边界、业务规则、持久化和外部组件的职责，说明为何这样划分，以及增加功能时需要修改哪里。

真实 Redis 缓存
对活动详情的基础信息做缓存，例如标题与总名额。剩余名额从 MySQL 查询，报名写路径不得以缓存余量为准。TTL 可配置，建议 30—300 秒；验证时可缩短。
提交能证明确实发生 Redis 写入、命中与过期的证据。Redis 不可用或读取失败时，活动查询应回源，核心报名仍能运行；连接和读取须有有限超时，并保留可定位日志。无需实现缓存预热、分布式锁或热点重建集群。
一张能演示的页面
页面必须真实调用后端：展示活动和剩余名额，输入演示用户 ID，选择活动报名，展示成功／业务错误，并查询“我的报名”。可用 Vue 3，也可用 HTML + JavaScript，无需美化或复杂路由。
对同一次报名意图的网络失败重试，保留原 requestId；新报名意图才生成新键。请求过程中应有基本状态提示，错误不能只输出到开发者控制台。
基础验证底线
提交至少三类验证证据：正常报名与重放、并发名额／业务去重、事务失败或组件故障。可使用提供的 Python 验收器，但不能把工具自带用例当作你自行设计了额外测试。
自动脚本只检查 HTTP 契约。数据库行数、剩余名额、真实缓存、回滚与重启后持久性仍须核对，不能只展示“接口返回成功”。

A  MQ 异步通知
报名成功后通过真实 MQ 发送事件，由独立消费者生成模拟通知记录；不需要真实短信或邮箱。重复投递同一事件不能生成重复通知。MQ 暂停时不能伪造报名失败或丢失已提交报名；说明并演示恢复／补发方式。
可使用 RabbitMQ、Kafka 或 RocketMQ。提交一条从报名 ID → 事件 → 消费 → 通知记录的证据链，以及一次重复消息或中断恢复测试。只使用进程内异步方法，不计为接入 MQ。
B  MongoDB 报名审计
将成功报名审计写入真实 MongoDB，支持按报名 ID 查询。重放同一事件只保留一份审计。MongoDB 不可用不能破坏已提交报名；提交恢复／补写证据，并明确 MySQL 与 MongoDB 的一致性边界。
C  Elasticsearch 活动搜索
从活动源数据建立真实索引，提供 GET /api/search/activities?keyword=...，能按标题查到固定活动。重复导入不产生重复文档；源数据变更后可重建或重同步，说明搜索可见时机。ES 不可用时应回源或返回明确的搜索服务错误，不影响核心报名。
无需中文分词插件；可以使用“Java”等可复现关键词。搜索不能取代 MySQL 对报名资格与名额的判定。
D  Python 数据对账工具
提供只读 Python CLI，读取专用数据库的活动／报名数据，输出每个活动的总名额、剩余名额、成功数及是否一致；同时检查重复报名或重复请求键。输出 JSON，正常退出码 0，存在不一致时非 0。
提供正常数据和故意构造的异常样例，证明能定位不一致并安全重跑。禁止默认自动修复或修改业务数据；解释并发写入期间如何获得一致的核对视图。可选调度，不要求部署 XXL-JOB。
统一评分：扩展架构与失败边界 4 分；真实运行 2 分、重复／一致性处理 2 分、故障或异常数据验证 2 分。技术名称、依赖声明和仅有设计说明，不能替代实现证据。

公开的关键验收
