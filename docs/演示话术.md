## 一、页面闭环演示（约 2 分钟）

打开演示页（真实调用后端，不是假数据）。

**业务场景（建议先说清楚）：**

> 用户在手机 App 点「立即报名」时，本地会生成一笔**客户端报名单号**（接口里的 requestId）。  
> - 网络卡住、用户连点提交：继续用**同一单号** → 幂等，不重复占名额。  
> - 用户退出后再进活动页，重新点「立即报名」：App 会**换新单号**；但同一用户对同一活动仍只能成功一次，后端返回 `ALREADY_REGISTERED`。  
> 单号作用域是「当前用户」：成功后绑定在该用户上。

**操作：**

1. 用户 ID 填 `1101`  
2. 刷新列表，指出固定数据：`1001` 开放、`1003` 零名额、`1004` 已关闭  
3. 选择 `1001`，保留当前「客户端报名单号」，点「提交报名」→ 新建成功  
4. **不点「重新点立即报名」**，再提交一次 → 同一单号重试，成功重放、不扣名额  
5. 查询「我的报名」  
6. 点「重新点立即报名」（换新单号），再对同一活动提交 → `ALREADY_REGISTERED`

**话术要点：**

> 页面区分两种操作：超时重试用旧单号；再次点击「立即报名」才换新单号。换了新单号也不能再占同一活动名额，因为业务去重认的是「用户+活动」。

## 二、边界用例口述 + 现场点验（约 3 分钟）

| 场景 | 怎么演示 | 期望 |
|---|---|---|
| 零名额 | 用户任意，活动 `1003` | `409 SOLD_OUT` |
| 已关闭 | 活动 `1004` | `409 ACTIVITY_CLOSED` |
| 同键跨活动 | 先对 `1005` 报名成功，再用**同一 requestId** 报 `1006` | `409 IDEMPOTENCY_CONFLICT` |
| 他人记录不可见 | 用用户 A 报名拿到 id，切换用户 B 查该 id | `404 REGISTRATION_NOT_FOUND` |

**判定顺序（考官常问，背这一段）：**

> 先校验身份与参数；  
> 再看同键重放/冲突、是否已报名；  
> **最后**才看活动是否关闭或满额。  
> 所以：已经成功的请求，即使活动随后满额，重放仍应返回原记录。

## 三、并发与一致性（约 2 分钟）

可直接说验收结果，必要时现场跑：

```bash
python tools/acceptance_test.py http://127.0.0.1:8080
```

重点报这三项：

1. **争抢名额**：多用户抢有限名额 → 成功数 = 名额，最终剩余 0，无超卖  
2. **同用户同键 20 并发**：1 次新建 + 19 次重放，**同一报名 ID**  
3. **同用户不同键 20 并发**：只允许 1 次成功，其余业务冲突

**实现一句话：**

> MySQL InnoDB 行锁 + 条件扣减保证名额；  
> `(user_id, activity_id)` / `(user_id, request_id)` 唯一键兜底；  
> 冲突后事务回滚，在事务外解释为重放或已报名，避免可重复读快照误判，也不把唯一键异常直接抛给客户端。

## 四、Redis 缓存边界（约 1.5 分钟）

**演示：**

1. 打开活动详情（或页面点刷新后看日志）  
2. 日志可见：`Redis MISS` → `Redis WRITE` → 再次访问 `Redis HIT`  
3. `redis-cli GET activity:base:1001`：只有 title/status/totalQuota，**没有 remainingQuota**

**话术：**

> 缓存只加速基础信息展示；  
> **剩余名额永远以 MySQL 为准**；  
> 报名写路径不读缓存余量。  
> Redis 超时很短，读失败就回源，核心报名仍可运行。

## 五、深化 D：对账（约 1.5 分钟）

```bash
python tools/reconcile.py --host 127.0.0.1 --port 3307 --user root --password root --database activity_reg
```

说明：

- 只读，不改业务数据  
- 检查：`总名额 == 剩余 + 成功报名数`  
- 检查重复用户活动、重复请求键  
- 一致退出码 0；故意造不一致时退出码非 0（见 `TEST_REPORT.md`）

**话术：**

> 并发写入期间可能短暂不一致，所以工具要求安全重跑，而不是自动“修复”。
